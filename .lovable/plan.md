- FinMind 實測（沙箱以 FINMIND_TOKEN 直呼）：單日全市場 10/02 可回傳 1,969 檔 → 上游沒壞，是排程時點抓太早（16:30 台北）抓到當日未出全的資料，且無補抓。

- PER 為 NULL 的紀錄佔 22%（虧損股，PE 正確地顯示不適用）。

## 一句話版本

每一把尺都是同一條公式：

```text
情境價 = 每股財報數字（分母）× 倍數區間
```

三把尺的差別只在「分母用哪個數字」：

| 尺 | 分母（每股多少） | 倍數的意義 | 回答的問題 |
|---|---|---|---|
| PE 本益比 | 每股獲利 EPS（近四季） | 股價是獲利的幾倍 | 這家公司「賺錢能力」值多少錢 |
| PB 股價淨值比 | 每股淨值（最新季末） | 股價是帳面淨值的幾倍 | 這家公司的「資產」值多少錢 |
| PS 股價營收比 | 每股營收（近四季） | 股價是營收的幾倍 | 這家公司的「生意規模」值多少錢 |

現金殖利率不是尺，只另列為輔助參考。

## 分母怎麼來（不能隨便算）

```text
每股獲利 = 歸屬母公司近四季淨利 ÷ 股數
每股淨值 = 最新季末股東權益 ÷ 股數
每股營收 = 近四季營收 ÷ 股數
```

股數的來源有優先順序，並且會標示可信度：

```text
① 官方 TWSE／TPEx 名錄（已核實）
② 官方名錄逾時 → FinMind 後備（特別股標示「待官方確認」）
③ 都沒有 → 標示「來源未知」，只說已計算
```

硬規則：
- 跨季配股、股票分割不會把不同口徑的數字直接相加。
- 分母只能用財報數字，禁止用股價反推分母（否則變成循環論證）。
- 虧損公司（近四季盈餘 ≤ 0）PE 直接標示「不適用」，不硬算。

## 倍數怎麼來（三個來源，都要交代依據）

```text
來源 A：本公司歷史
  近 5 年每日倍數 → 去掉極端 5%（winsorize）→ 取 30–70 百分位區間
  樣本 < 250 天 → 標示「樣本不足」，只稱「歷史情境參考」

來源 B：同業比較
  同細分產業 ≥ 3 家 → 取中位數（極端值先剔除）
  < 3 家 → 標示「同業不足」，不產生同業倍數

來源 C：你自己填（我的情境試算，僅此裝置）
  自填預期分母＋倍數上下限＋來源＋日期
  期間不一致會被阻擋（例：歷史 TTM 倍數 × 未來 EPS → 不給算）
```

每個倍數都必須附上：選擇理由、樣本數、資料期間。

## 一把尺的完整流程（以 2454 為例的數字長相）

```text
現價 ──────────────────────────────────────────────►

分母：近四季每股獲利 = 60.69 元（財報，已核實 3/3）
倍數：歷史 30–70 百分位 = 假設 40–55 倍（樣本 1,200 天）

情境價 = 60.69 × 40 ~ 60.69 × 55
       ≈ NT$2,428 ~ NT$3,338

現價隱含倍數 = 現價 ÷ 60.69（只描述「現價等於幾倍」，不說貴或便宜）
```

## 三把尺「不做」的事（同樣重要）

```text
✗ 不把三把尺的區間取交集當「系統合理價」
✗ 不把歷史最高／最低倍數稱為合理價
✗ 不把現價隱含倍數說成「高估／低估」
✗ 不給機率百分比（沒有校準模型，機率就是未知）
✓ 資料不足就明說「尚不能判定合理價」，仍顯示已核實的分母
```

## 圖形化呈現（抽屜裡的樣子）

```text
目標價 │ PE │ PB │ PS   ← 四段切換，共用同一條 NT$ 等比例軸
───────┴────┴────┴────
        成本    現價        目標價
────────●───────●──────────●──────────► NT$
              [═══ 情境帶 ═══]          ← 只有選定的那把尺、且有依據才畫

尺下方一行白話：
「以你選的 20–25 倍，現價 NT$4,980 需要每股獲利 NT$199–249
 （這是現價反推要求，不是合理價）」
```

- 切換 PE／PB／PS 時用動畫滑動，軸的比例尺不變、不斷軸。
- 某把尺資料不足 → 該段不畫區間，直接寫原因（例：「TTM 盈餘≤0，PE 不適用」）。
- 三把尺永遠各自獨立呈現，不合併成一個「答案」。

## 為什麼這樣設計

1. **分母必須是財報事實**：股價是市場投票結果，不能拿來證明股價合理。
2. **倍數必須有出處**：歷史、同業、或你具名的來源，三者擇一並揭露。
3. **不製造假確定性**：與其給一個漂亮的「合理價」，不如誠實說「目前證據只能講到這裡」。

## 修復計畫（估值資料鏈，待核准後執行）

範圍：只動排程與回補（cron、valuation-sync、backfill）與告警；不動 RLS、不動抽屜計算邏輯、不發布正式站。

1. **立即回補缺日（9/23–10/06）**
   - 以 `valuation-sync` `market_day` 模式逐日重跑（ FinMind 現已可回傳全量，每日 1 次 API，7 個交易日 ≈ 7 次請求）。
   - 回補後驗證：每日 rows 回到 ≈1,900+，並抽 3443／2454 讀回抽屜顯示。

2. **market_day cron 防呆**
   - 每交易日跑兩次：收盤後一次（16:30 台北）＋晚間補跑一次（如 22:00 台北），晚間只在當日 rows < 1,500 時執行，避免重複 API。
   - 每次執行寫 `system_jobs_log`（成功／失敗／upserted 數），rows 異常偏低（<1,500）時寫入 `system_alerts`。
   - 失敗重試走既有 `fetchWithRetry`；連續失敗升級 alert。

3. **歷史回補加頻**
   - `valuation-history-backfill` 由每週六 120 檔改為每交易日一批（limit 120、min_rows 250），優先順序：活躍持倉母體 → 樣本不足清單（既有 `valuation_backfill_targets`）。
   - 追平後維持每日巡檢一次即可。

4. **額度檢視**
   - 盤點 240／日是否足夠（market_day 1 次＋backfill 120 次＋估值抽屜冷啟）；不足則調高 `finmind_quota_pools` 預算或在金流商加購 FinMind 方案，先列數據給你決定。

5. **驗收 gate**
   - 回補後：`tw_valuation_daily` 最近 10 個交易日每日 rows ≥ 1,500。
   - 抽屜實測 3443、2454、一檔虧損股：歷史倍數可用／PE 不適用文案正確。
   - 單元測試：market_day 低 rows 觸發 alert 的邏輯；cron 雙跑不重複 API（第二次 gate 生效）。
   - 全量測試、tsgo、build 通過；不發布正式站。
